# How the uniform controller works

The controller reads all four exact GPU UUIDs once per second and selects their highest valid core temperature. It sends one integer fan target to all eight fans. Physical slot order is recorded for the study, but does not select the controlling card.

The separately stored JSON table defines the temperature demand. Demand is linearly interpolated and rounded upward between knots. During ordinary heating, the command can increase by two percentage points per second. Cooling uses a three-second exponential filter, a three-point deadband, a20-second dwell and one-point reductions no more often than every10 seconds. Unchanged targets are not rewritten. The published selected `controller/gpu-profile.json` is the authority for the actual knots and startup setting; policy defaults are not the selected profile.

After at least30 seconds of quiet activity, a new load rearms the short startup floor. Active work retains at least65% fan demand. Once every card is below65 C and under10% utilization for30 seconds, the idle path can reduce the common command by five points every five seconds toward the cool curve. The preferred75–80 C load band does not require warming an idle card deliberately.

At81 C and above, raw hottest temperature can invoke the protective table without waiting for the cooling filter. Protection is gradual:81/83%,82/86%,84/92%,85/95%,88/100%. A fresh controller restart starts at no less than80% or the hotter protective demand, so restarting at88 C cannot reset100% cooling to a lower cold-start setting. The90 C qualification cutoff records a persistent critical latch and suspends owned inference while retaining strong observable cooling. Persistent critical work permits an identity-validated owned-cgroup kill. Critical inference does not resume automatically.

The primary owns a permanent exclusive kernel lease. The independent observer reads the four GPUs separately, checks current-boot freshness and fan/cap confirmations, and supervises the primary's behavior. Both root services have six-second watchdogs and automatic restart supervision. A stopped process keeps its lease until actually terminated; a second writer cannot acquire it. Cleanup restores NVIDIA automatic policies using the documented default-fan API and verifies all eight policies.

Automatic control is a short recovery bridge under heavy load: this stack's automatic baseline reached90 C in about four minutes. A root-owned, nonrenewable recovery epoch survives process restarts, allowing confirmed automatic handoff before suspending inference if custom protection cannot return. The intended handoff bound is15 seconds and the custom-recovery request threshold30 seconds. Receipts report observed restoration/readiness/suspension timings; the request threshold is not a promise of zero-latency confirmation.

Owned suspension first uses a bounded Docker pause. If Docker communication is unavailable, a validated exact container identity, process start time and cgroup can freeze only that owned runtime. Docker's `Paused` field can differ from a direct kernel freeze. Explicit unfreeze requires fresh protection and no critical latch. Foreign containers are outside this control boundary.

Independent status inspection distinguishes protection readiness from model API readiness. Fan percentage/RPM are driver-reported operating observations. This implementation is deterministic software, not a model-generated real-time decision, and its fault proofs do not establish immunity to all physical fan, driver, kernel or power failures. See `FAULT-EVIDENCE.md` for the actual tested paths and `OPERATIONS.md` for update, rollback and automatic restoration.
